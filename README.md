# VoIP Margin Console

Web version of the margin dashboard. The UI is unchanged; what changed is where
the data lives.

The original was one 5.4 MB HTML file with ~48,000 rows of buy/sell rates,
margins, credit exposure and payment terms compiled into it. That file could not
be published anywhere public, and refreshing it meant regenerating the whole
thing.

Now:

- **`public/`** is the site — about 42 KB and **contains no business data**.
  Safe to publish on GitHub Pages.
- **Supabase** holds the data, behind row level security. A visitor without a
  login gets a sign-in box and nothing else.
- The render logic is byte-for-byte the original, just wrapped in a
  `bootConsole(DATA)` function that receives the same six objects it always
  read. No behaviour changed.

## Layout

```
public/            published to GitHub Pages — no data in here
  index.html       generated by scripts/build_app.py, do not hand-edit
  auth.js          login gate + payload loader
  config.js        your Supabase URL + anon key (safe to commit)
scripts/
  extract_from_html.py   original HTML -> data/*.json  (one-off)
  build_app.py           original HTML -> public/index.html
  seed_supabase.py       data/*.json -> Supabase
  import_csv.py          CSV -> Supabase (the monthly refresh)
  serve_local.py         local dev server, no Supabase needed
supabase/
  schema.sql       tables, RLS policies, get_console_payload()
  .env             your service_role key — gitignored
data/              extracted datasets — gitignored
```

`data/`, `supabase/.env` and any `*.csv` / `*.xlsx` are gitignored. That is
load-bearing, not tidiness: the published site is world-readable.

## Run it locally right now

No Supabase account needed. This is also how to run it offline.

```powershell
python scripts\serve_local.py
```

Then open <http://localhost:8000/?local>. The server builds the same payload
Supabase would return, out of `data/*.json`.

The `?local` path only works on `localhost` — it is gated on hostname, so it
cannot be triggered on the published site.

## Setting up Supabase

1. Create a project at <https://supabase.com> (the free tier is far more than
   this needs — the whole dataset is about 6 MB).

2. **Dashboard → SQL Editor → New query**, paste all of
   [`supabase/schema.sql`](supabase/schema.sql), run it. This creates the
   tables, turns on row level security, and creates `get_console_payload()`.

3. **Project Settings → API**, copy two values:
   - *Project URL* and *anon public* key → into
     [`public/config.js`](public/config.js). Both are meant to be public; the
     anon key grants nothing on its own because every table requires an
     authenticated session.
   - *service_role* key → copy `supabase/.env.example` to `supabase/.env` and
     put it there, along with the project URL. **This key bypasses RLS
     entirely.** It never goes in `public/`.

4. Load the data:

   ```powershell
   python scripts\seed_supabase.py
   ```

   About 55,500 rows across eight tables; takes a couple of minutes.

5. **Dashboard → Authentication → Users → Add user** for each person who needs
   access. Set *Auto Confirm User* so they can sign in immediately.

   Under **Authentication → Providers → Email**, turn **off** "Enable sign-ups".
   Otherwise anyone who finds the URL can create their own account, and an
   authenticated account is exactly what the RLS policies trust.

## Publishing to GitHub Pages

The repo can be public — there is no data in it — but a private repo needs a
paid plan for Pages, so public is the practical choice. Check `git status`
before the first push and confirm no `data/` or `.env` files are listed.

```powershell
cd C:\Users\Mohammed\voip-margin-console
git init
git add .
git status                      # verify: no data/, no .env, no *.csv
git commit -m "VoIP Margin Console: Supabase-backed web app"
git branch -M main
git remote add origin https://github.com/<you>/voip-margin-console.git
git push -u origin main
```

Then **Settings → Pages** on the repo: source *Deploy from a branch*, branch
`main`, folder **`/public`**. The site appears at
`https://<you>.github.io/voip-margin-console/` within a minute or two.

Finally, in Supabase go to **Authentication → URL Configuration** and add that
URL to *Site URL* / *Redirect URLs*.

## The monthly refresh

Export from the billing system, shape it into one CSV per table, then:

```powershell
python scripts\import_csv.py --dry-run routes exports\routes.csv
python scripts\import_csv.py routes exports\routes.csv
```

`--dry-run` validates without writing. Each run replaces the table unless you
pass `--append` (which is what you want for `daily_carrier` when adding a new
month). Run `python scripts\import_csv.py --help` for the table list; the
required column headers for each are in `SCHEMA` at the top of that file.

**This is the one part that is not finished.** The importer validates and loads
CSVs whose headers already match the schema, but the mapping *from* your billing
system's export columns *to* those headers does not exist yet — I did not have a
sample export to write it against. Send one and that step can be automated too;
until then it is a manual reshape in Excel.

Two other things worth knowing:

- `routes.id` and the `trunk` column are positionally paired in the payload.
  If you renumber `routes.id`, trunk names will attach to the wrong routes.
  Keep the ids contiguous from 0, in the order the rows should appear.
- `am_breakdown`, `am_totals` and `carriers` are pre-aggregated summaries, not
  derived from `routes` at query time. If you refresh `routes` you must refresh
  those too, or the Account Manager and All Carriers tabs will show stale
  totals.

## Rebuilding the front-end

`public/index.html` is generated. If the original console is updated, re-run:

```powershell
python scripts\build_app.py <path-to-new-original.html>
```

It refuses to write output if any dataset is still embedded, so a regression
there fails loudly rather than quietly publishing rates.
